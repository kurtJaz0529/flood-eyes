### 4. 修掉一个真实启动 bug（重要）

**现象**：在设置了 `HTTP_PROXY`/`HTTPS_PROXY` 的机器上，程序启动即退出，`logs/desktop.log` 只留一行权重提示。
源码方式启动可复现：

```
gradio\blocks.py line 3175 in launch
    resp = httpx.get(f"{self.local_api_url}startup-events", verify=ssl_verify, timeout=None)
httpx.ConnectTimeout: [WinError 10060] ...
```

**原因**：Gradio 启动时会请求**它自己的** `http://127.0.0.1:<port>/startup-events`，而 `httpx.get`
默认 `trust_env=True`，于是这个本机请求被送到 `HTTP_PROXY` 去转发；代理拒绝/超时后 `launch()` 抛
`ConnectTimeout`，进程直接退出。用户看到的就是"双击没反应"。

**修复**：`app/desktop.py` 新增 `bypass_proxy_for_localhost()`，在启动前把 `127.0.0.1 / localhost / ::1`
追加进 `NO_PROXY`（只加回环地址，用户代理原样保留，在线地图与卫星下载不受影响）。

**验证**：在**保留**代理环境变量的条件下启动源码版，端口正常监听：

```
7897 -> OPEN (修复生效，代理环境变量下也能启动)
[trace] build_ui returned / queue configured / launch attempt 0 on port 7897 / launch returned
```

### 4.1 冻结版端到端启动验收未通过 —— 但根因不在代码

`scripts/verify_packaged_app.py`（你重写的那个）我跑过两次，都在"服务端口就绪"这一步失败：

```

检测到权重 0 个（将使用 NDWI 基线）
```

为了定位，我编了一个 `FLOOD_CONSOLE=1` 的调试版并用 `faulthandler` 抓到了确切的卡点堆栈：

```
Timeout (0:01:15)!
Thread 0x000065dc (most recent call first):
  File "socket.py", line 295 in accept
  File "socket.py", line 627 in _fallback_socketpair
  File "asyncio\proactor_events.py", line 786 in _make_self_pipe
  File "asyncio\windows_events.py", line 316 in __init__
  File "asyncio\events.py", line 734 in new_event_loop
  File "gradio\utils.py", line 124 in safe_get_lock
  File "gradio\queueing.py", line 137 in __init__
  File "gradio\blocks.py", line 2586 in queue
  File "gradio\blocks.py", line 1214 in __init__      ← gr.Blocks(...) 构造
  File "app\main.py", line 961 in build_ui
  File "desktop.py", line 290 in main
```

链路是：`gr.Blocks()` → `queue()` → `asyncio.new_event_loop()` → Windows proactor 建自管道 →
`socket.socketpair()`。**Windows 上没有 `_socket.socketpair`**（已实测 `hasattr(socket._socket,'socketpair') is False`），
所以 Python 走 `socket.py` 的 `_fallback_socketpair`，其中需要一次 **127.0.0.1 回环连接**，
随后 `listener.accept()` **永久阻塞**。

**根因是执行环境的进程级网络限制，不是代码**，三条对照证据：

1. 源码方式启动（`python app/desktop.py --headless`）**正常**，同一台机器、同一份代码。
2. 本机**已安装的旧版 v0.2.0**（此前跑通过，日志里有完整启动横幅）**现在同样卡在同一行**。
3. 把 `python.exe` 复制一份改名成 `zz_unknown_probe.exe` 再跑 `socket.socketpair()`：**25 秒超时无输出**；
   原版 `python.exe` 跑同一句是 **0.001 秒成功**。

即：**"未知"可执行程序在本机发起回环连接会被拦住**（本机装了腾讯电脑管家 `QQPCRTP.exe` 等安全软件，
叠加 WorkBuddy 的命令安全策略）。冻结版 exe 正是"未知程序"，所以起不来；而 python.exe 在白名单里。
我这边还试过 `dangerouslyDisableSandbox` 无隔离运行，同样卡住，说明不是 WorkBuddy 沙箱单方面造成。

**结论与建议**：这一项**必须在正常用户会话里验证**（双击安装包 → 安装 → 双击启动），
或者把 `慧眼识灾.exe` 加入安全软件白名单后再跑 `scripts/verify_packaged_app.py`。
不要因为这次失败去改 `build_ui` 或 Gradio 版本——那会掩盖真实原因。若要加防御，看门狗已经能把它变成可诊断日志。
